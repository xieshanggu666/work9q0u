# 末日地堡生存

一款基于 **FastAPI + SQLite** 后端与 **Vue 3（本地运行时，离线可用）** 前端的末日地堡模拟经营游戏。

## 游戏说明

地表已覆灭，你带领一批幸存者藏身地堡。你需要管理**有限的食物、水源、电力、氧气**，安置与分配**居民岗位**，扩建**基础设施**，并在每天的**危机轮盘**中做出抉择，坚持到第 120 天迎来曙光。

## 核心机制

- **资源守恒循环**：每日净变化 = 设施产出 − 人口消耗。产出受设施等级、相关岗位（农民/工程师）与平均士气加成影响。
- **四类资源**：食物 / 水源 / 电力 / 氧气，任一枯竭都会引发减员。
- **居民管理**：每位幸存者有健康与士气，健康低于阈值士气下滑；士气影响整体产出效率。可为居民指派岗位（工程师 / 农民 / 医护 / 杂工）。
- **设施扩建**：穹顶菜园（产食物）、净水器（产水）、发电机（产电）、水培制氧（产氧）、医疗舱（被动回血）、医疗救治中心（病例收治）、仓储区。可建造与升级（等级加成 x1.6）。
- **医疗救治中心**：受伤或染疫居民经历 **登记 → 治疗/隔离 → 康复/病亡** 的完整病例链。每级中心提供 2 张救治床位，每名当值「医护」再加 1 床并提升救治效率；治疗/隔离按床每日消耗食物、水源与电力，物资不足当日停诊。登记未收治病例会持续恶化，未隔离的传染病例可能在堡内扩散（医护越多传播概率越低），隔离即切断传播。疫病危机、探索/押运途中受伤会在结算后自动建档；在治病例暂停生产，有未结病例者不得离堡，离堡成员的病例随队伍冻结、回堡后续治。终局按登记/康复/病亡/累计救治床日做危机后健康结算。
- **危机轮盘**：每天约 45% 概率触发危机事件，均可多选决策（辐射风暴、内讧、氧气泄漏、疫病、盗匪、物资舱、暴雪、路过商队），不同选择带来不同的资源 / 健康 / 士气 / 信誉后果。
- **贸易救援**：在「贸易救援」页联络外部聚落，市场每日轮换四条报价（紧急求援 / 对外采购）。订单走 **申请 → 审核 → 押运运输 → 交付 / 失败回退** 状态链：申请时冻结托管物资，外部聚落按地堡信誉掷审核；通过后押运队离堡（与探索队同口径：暂停生产、不耗地堡口粮、不参与地堡危机），在途可能触发途中事件（截道 / 沙暴 / 盘查 / 故障），途中货损按残存比例结算；成功则回礼/采购入库并提升信誉与士气，失败（交易黄了 / 弃货 / 全损 / 全员失联）则剩余货物退回、扣信誉。终局日订单强制安全收敛，不留僵尸订单。
- **结局结算**：存活至第 120 天**胜利**；人口归零或四资源全线枯竭则**失败**。胜局 / 败局均按幸存者 × 天数 × 士气系数结算评分。

## 技术栈

| 层 | 技术 |
|---|---|
| 后端 | Python 3.10+ / FastAPI / SQLAlchemy 2.0 / SQLite |
| 前端 | Vue 3 单页应用（vue.global.prod.js 本地运行时，hash-free 组件切换，无需构建工具） |

## 快速开始

环境要求：**Node.js**（任意近年版本，仅用于命令调度，前端无需构建）与 **Python 3.10+**。
前端静态资源由 FastAPI 后端同端口托管，因此一条命令即可启动前后端：

```bash
npm run setup   # 安装 Python 依赖并初始化数据库（仅需一次）
npm start       # 一键启动前后端
```

访问 http://127.0.0.1:8000 ，在档案大厅新建或继续一局游戏。

| 命令 | 作用 |
|---|---|
| `npm run setup` | 安装 Python 依赖 + 初始化数据库（幂等，含演示档案） |
| `npm start` | 生产模式启动（`PORT=8080 npm start` 可换端口，`HOST`/`PYTHON` 同理） |
| `npm run dev` | 开发模式启动（代码变更自动重载） |
| `npm run init-db` | 仅初始化/补齐数据库 |
| `npm test` | 运行 pytest 测试套件（`npm test -- -k xxx` 可透传参数） |

## 状态流转与一致性约定

档案状态机只有四个阶段，所有后端守卫以前端禁用为辅助、以后端校验为准：

| 阶段 | 含义 | 允许的动作 |
|---|---|---|
| `daily` | 每日阶段 | 建造/升级/调岗/登记收治病例/派遣探索队/申请或撤单贸易/推进一天 |
| `crisis` | 地堡危机待处理 | 仅结算当前危机 |
| `expedition` | 探索遭遇待处理 | 仅结算当前遭遇 |
| `trade` | 押运途中事件待处理 | 仅结算当前途中事件 |
| `ended` | 胜利/失败终局 | 只读，拒绝一切变更 |

- **待决事件统一管线**：每日危机、探索遭遇、押运途中事件三类挂起抉择共用同一套机制（`engine.py` 的 `_PENDING_SLOTS` 槽位注册表）——同构快照（token/事件/目标/选项）随档案落库、刷新后恢复同一场抉择；档案级幂等凭据（`last_resolution` / `last_expedition` / `last_trade`）支持连点与并发落败安全回放；同一互斥状态机（任一抉择挂起即锁定经营与推进）；终局一次性清空全部槽位。存储位置保持原样（`pending_crisis` 列、`expedition.pending_encounter`、`trade_order.pending_incident`），旧存档无需迁移即可加载。
- **每日推进**：`daily → 产出消耗/健康士气 → (行军+遭遇? | 危机? | 终局)`。抉择不可被“再点一天”跳过。
- **探索队**：离堡人员暂停地堡生产、不消耗地堡口粮、不参与地堡危机效果；行军消耗自带口粮，遭遇替代当日地堡危机，返程统一结算战利品/余粮/伤亡。终局日队伍仍在外时先安全返程再收敛到 `ended`，不留“僵尸队伍”。
- **贸易救援**：订单与探索队互斥（同一时间只允许一支在外队伍/一笔在谈订单）。审核中（`reviewing`）押运队仍在堡正常生产，可随时撤单且托管全额退还；审核通过进入在途（`transporting`）后不可撤单。押运队在途口径与探索队完全一致（暂停生产/口粮、跳过地堡危机与医疗舱）。途中事件挂起进入 `trade` 阶段并替代当日地堡危机；弃货/全损/全员失联在事件结算时当场收敛为失败回退，抵达日再掷一次交付（成功率随信誉）。失败回退按残存比例退还托管（求援未送达/采购货损），成功入库同样遵循"终局裁决先快照"——全线枯竭当日的回礼不会复活败局。
- **并发**：`row_version` 乐观锁保证每日推进/危机/遭遇/途中事件只落一次；落败方凭一次性 `token` 与档案级幂等凭据（`last_resolution` / `last_expedition` / `last_trade`）安全回放，过期或串档请求返回 409。
- **旧存档**：启动时自动补列（`pending_crisis` / `last_resolution` / `expedition` / `last_expedition` / `trade_order` / `last_trade` / `medical_cases` / `reputation` / `row_version`），并归一化损坏/悬空快照（已结束档案清除悬而未决状态、失踪成员/目标剔除、悬空/重复或绑定死者的病例收敛、`survivors` 与居民表对齐），归一化本身幂等。
